# 第 23 天：FastAPI 版与 Dify 版对比

对比日期：2026-10-26。结论：本项目继续用代码版承载定制业务，Dify 版用于快速验证知识问答原型和低代码交付。代码版的优势在于控制业务细节；Dify 版的优势在于通过可视化配置组合已有能力。两者的回答质量仍需同条件评测。

## 当前实现对比

| 维度 | FastAPI + LangChain 代码版 | 本次 Dify 简化版 |
| --- | --- | --- |
| 搭建与修改 | 自行维护 React 页面、API、Prompt、检索和存储；开发工作较多，修改逻辑可直接落到代码 | 在控制台配置模型、知识库、Prompt 和引用，使用现成问答页面；应用配置可导出 DSL |
| 检索控制 | 支持关键词检索及 ChromaDB 向量检索模式；向量未可靠命中时可配置关键词回退，记录实际检索方式 | 使用原生 Economy 关键词索引，top_k=3；本次未配置 Embedding 或重排 |
| Agent 与业务 | 已封装知识库 StructuredTool、意图分类、Query Rewrite 和结构化流程字段提取 | 本次为基础 Chatbot，仅根据四份文档回答，不执行流程申请 |
| 流程集成 | 用户编辑字段并确认后调用 n8n；先写 SQLite，按 request_id 拒绝重复提交，提供状态查询 | 本次未接 n8n，也未实现申请编号与执行记录；这是当前复刻范围，不是 Dify 的能力上限 |
| 排错与验证 | 可定位检索、模型、字段校验和 Webhook 代码；已有检索记录、流程记录及测试，尚未统一全链路 Trace | 可在控制台调整应用配置，通过 API 报告与页面核对回答；定位底层故障仍需检查容器或插件日志 |
| 部署与维护 | 维护自有前后端、SQLite/Chroma 数据，以及独立 n8n 服务 | 应用配置集中，但本机自托管仍需维护多容器、模型插件和数据；低代码不等于零运维 |
| 交付与迁移 | 代码、配置样例、测试和文档纳入版本管理；业务规则变更需要开发与验证 | 已导出 DSL；迁移仍需导入文档、重建索引、配置模型凭据并重新绑定知识库 |

代码依据：[检索服务](../backend/rag/service.py)、[知识库 Tool](../backend/rag/tools.py)、[字段提取](../backend/services/process_extraction.py)、[流程提交](../backend/services/process_submission.py)。Dify 配置依据：[应用 DSL](../integrations/dify/enterprise_knowledge_chatbot.yml)与[部署说明](../integrations/dify/README.md)。代码版支持向量检索，不代表每次请求都走向量模式，实际行为取决于配置和回退结果。

## 已验证的结果与公平比较方式

[第 22 天验收](day22_dify_acceptance.md)中，Dify 的年假、报销、GitLab 权限、VPN 和无依据拒答共 5 条真实 API 用例通过，页面也核对了主要问答与拒答。来源列表仍可能包含不相关文档，不能宣称引用精确率 100%。代码版的流程页面验证见[第 21 天记录](day21_frontend_acceptance.md)，其中开发验证使用模拟模型/n8n 与临时 SQLite，不能当作两版在线效果对照。

第 24～25 天用同一组四份文档、相同问题与独立对话，对照检索来源、回答引用、关键词覆盖和拒答正确性，并记录模型名称、Prompt、索引方式及参数。流程意图与申请提交单独验收，不把 Dify 本次未实现的流程功能计作问答失败。当前没有同条件的两版质量、耗时或成本报告，不给出优劣排名。

## 选型与下一步

需求是制度 FAQ、快速演示或经常调整 Prompt，且现有组件能够满足时，优先用 Dify 验证和交付；需求涉及自定义检索范围、字段协议、重复提交控制、状态恢复或业务系统集成时，本项目继续采用代码版。当前的“流程成功”仅表示收到模拟回执且已落库，不代表审批通过或权限已开通。

借鉴参考项目 [LangChain-Agent](https://github.com/Cai-Chang/LangChain-Agent) 时，后续优先补统一 request_id 的执行轨迹、独立业务校验和真实执行日志页面；先用评测证明问题，再决定是否引入 LangGraph。本次只完成方案对比，不扩展 Agent 编排或改写业务代码。
